# ClickHouse (+ Redash / Airflow) observability feature landscape — what a read-only fleet monitor should have beyond cobserve today

Scope note: cobserve today = node memory/CPU with per-user share (view 1), running queries, Redash RQ queue (2), fleet map (3), event tape (4), Airflow's day (5), Jira (6), embedded Claude/SQL sessions (7+), local machine (0). Everything below is what the surveyed tools do that cobserve does not, with the system tables/SQL that would feed it on ClickHouse 24.10/24.11 over HTTP with a read-only user holding `SELECT ON system.*`. Research date: 2026-10-13. Where a source could not be fetched (GitHub tree pages, terminaltrove returned 403/404) that is said explicitly.

## Key question 0 — Prioritised candidate list (synthesis of everything below)

### Takeaway
The biggest gaps between cobserve and best-in-class read-only ClickHouse monitors are (a) **history** — cobserve has 4 minutes of sparkline, everything else reads `system.query_log` / `system.metric_log` / `system.part_log` for hours or days; (b) **the write path** — parts, merges, mutations, replication, inserts, which cobserve does not show at all although they are what actually pages an on-call; (c) **per-query forensics** (ProfileEvents, EXPLAIN, query_metric_log, text_log per query) which chdig has made the standard. Everything in the table is read-only and available on 24.10/24.11 unless flagged.

Workflow features the surveyed tools add (all read-only except KILL): fuzzy "command palette" over views+actions (chdig `Ctrl-P`), copy query to clipboard (`y`), save/share logs (`s`/`S`), open EXPLAIN PIPELINE graph in browser (`G`), pause (`p`), follow-item (`Home`), split panes (`Alt+=`/`Alt+-`), column reorder/hide by mouse, filter predicates (`user=default elapsed>10s mem>1G pe.<ProfileEvent> s.<setting>`) ([Actions.md](https://github.com/azat/chdig/blob/main/Documentation/Actions.md), [Queries.md](https://github.com/azat/chdig/blob/main/Documentation/Queries.md)). KILL QUERY, DROP, SYSTEM are out for cobserve; chdig's `K` and Tabix's KILL exist only as "the user's own client".

### Inferences
- Rows 2–6 are cheap (in-memory system tables, single-digit ms), fit the 1.5 s poll, and map directly onto cobserve's existing insight/tape machinery — they are the highest value-per-line.
- Rows 1, 8, 9, 14 all need a second, slower poll class (every 30–60 s, or on demand) against `*_log` tables; designing that "history lane" once unlocks four features.
- Row 15 is where chdig shines but is the wrong fit for a read-only monitoring user and a data-engineer audience.

### Gaps
- Whether Paysera's fleet uses Kafka engine, S3Queue, Distributed tables, dictionaries or BACKUP is not in the context file; row 12's value depends on it.
- `part_log`, `query_views_log`, `query_metric_log`, `text_log` must be enabled in server config; which of them are on in the fleet is unknown.

## Key question 1 — chdig: all views, what each shows, the keyboard model, what users use most

### Takeaway
chdig is a `top`/`csysdig`-style TUI that wraps essentially every `system.*` table into a view, with per-query drill-downs (details, ProfileEvents, EXPLAIN, logs, flamegraphs), a fuzzy command palette, tmux-like panes, time seeking into rotated log tables, and a `--cluster` mode. Its documented differentiators are flamegraphs and query views; its issue tracker is dominated by packaging, not features.

### Cited Findings
- README headline features: "top like interface (or csysdig to be more precise)", "Flamegraphs (CPU/Real/Memory/Live) with auto-refresh and diff highlighting", Perfetto export, "Shareable flamegraphs via pastila.nl and speedscope", "Shareable logs through pastila.nl", "Shareable query pipelines using viz.js", "Split panes (tmux-like)", "Views configuration with startup pane layout options", "Cluster support for aggregating data across hosts", "Historical support including rotated system log tables", "Compatible with clickhouse-client options and configuration files"; status "Pre-alpha … keyboard shortcuts, views, and color schema" may change; oldest tested ClickHouse 21.2 — [chdig README](https://github.com/azat/chdig)
- Queries views: default view is `system.processes` "displaying CPU, IO/CPU wait, memory, disk/network usage, and subquery counts"; **Query Patterns** groups by `normalized_query_hash` "with duration distribution", "~25 metrics" toggled via Space/`m`: "duration, CPU/IO/network time, memory, bytes read/written, parts/ranges/marks selected, exceptions, and threads" — [Features.md](https://github.com/azat/chdig/blob/main/Documentation/Features.md)
- **Slow queries** (`chdig slow-queries`): "queries exceeding 1 second duration"; **Last queries** (`chdig last-queries`): recently completed; both from `system.query_log`; time window via `--start/--end` and interactive seeking — [Queries.md](https://github.com/azat/chdig/blob/main/Documentation/Queries.md)

## Key question 2 — ClickHouse's own monitoring surfaces: `/dashboard`, `system.dashboards`, and the system tables, with on-call questions and cheap SQL

### Takeaway
ClickHouse ships a complete reference design in `system.dashboards`: 19 "overview" charts (and a per-`hostname` variant, a memory dashboard, and cloud variants) each with a parameterised SQL over `merge('system','^metric_log')` / `asynchronous_metric_log`. Porting those queries verbatim is the cheapest path to a defensible history view; the remaining system tables each answer one on-call question with one cheap SELECT.

### Cited Findings
**Built-in dashboard**
- `/dashboard` (auth required) shows "Queries/second, CPU usage (cores), Queries running, Merges running, Selected bytes/second, IO wait, CPU wait", OS CPU user/kernel, disk and filesystem reads, memory, "Inserted rows/second, Total MergeTree parts, Max parts for partition"; metrics live in `system.metrics`, `system.events`, `system.asynchronous_metrics`, with history in `asynchronous_metric_log`; also `/ping` (200) and `/replicas_status` (503 when delayed) — [Monitoring docs](https://clickhouse.com/docs/operations/monitoring)
- `system.dashboards` "stores queries that power the /dashboard page", one row per chart; parameters `{rounding:UInt32}`, `{seconds:UInt32}`, `WITH FILL STEP` — [system.dashboards docs](https://clickhouse.com/docs/operations/system-tables/dashboards)
- Full chart list of the `overview` dashboard (from source): Queries/second `avg(ProfileEvent_Query)`; CPU Usage (cores) `avg(ProfileEvent_OSCPUVirtualTimeMicroseconds)/1000000`; Queries Running `avg(CurrentMetric_Query)`; Merges Running `avg(CurrentMetric_Merge)`; Selected Bytes/second `avg(ProfileEvent_SelectedBytes)`; IO Wait `avg(ProfileEvent_OSIOWaitMicroseconds)/1e6`; CPU Wait `avg(ProfileEvent_OSCPUWaitMicroseconds)/1e6`; OS CPU Usage (Userspace/Kernel) from `asynchronous_metric_log` metric `OSUserTimeNormalized`/`OSSystemTimeNormalized`; Read From Disk `avg(ProfileEvent_OSReadBytes)`; Read From Filesystem `avg(ProfileEvent_OSReadChars)`; Memory (tracked) `avg(CurrentMetric_MemoryTracking)`; In-Memory Caches `arraySum([COLUMNS('CurrentMetric_.*CacheBytes') EXCEPT 'CurrentMetric_FilesystemCache.*' APPLY avg])`; Load Average (15 minutes); Selected Rows/second `avg(ProfileEvent_SelectedRows)`; Inserted Rows/second `avg(ProfileEvent_InsertedRows)`; Total MergeTree Parts (async `TotalPartsOfMergeTreeTables`, avg); Max Parts For Partition (async, `max(value)`); Concurrent network connections `max(CurrentMetric_TCPConnection/MySQLConnection/HTTPConnection/InterserverConnection)`. ## Key question 3 — "Top queries" analytics from query_log; how Cloud Query Insights, Altinity, chmonitor, Tabix, DBeaver do it

### Takeaway
Every tool converges on the same shape: group `query_log` by `normalized_query_hash` (and user), rank by a cost (duration×runs, memory, read bytes), show p50/p90/p99 and error rate over time, and drill into one representative run with its ProfileEvents and Settings. ClickHouse's own diagnosis guide gives the canonical SQL; Cloud Query Insights is the reference UI; Tabix/DBeaver do not do this.

### Cited Findings
- Canonical pattern query (ClickHouse docs): `SELECT normalized_query_hash, count() AS executions, quantile(0.5)(query_duration_ms) AS median_duration_ms, max(query_duration_ms) AS max_duration_ms, formatReadableSize(avg(read_bytes)) AS avg_read_bytes, formatReadableSize(max(memory_usage)) AS max_memory, any(query) AS example_query FROM merge('system', '^query_log') WHERE type = 'QueryFinish' AND is_initial_query = 1 AND query_kind = 'Select' AND event_time >= now() - INTERVAL 1 HOUR GROUP BY normalized_query_hash HAVING executions >= 2 ORDER BY median_duration_ms DESC LIMIT 10`; then pick a representative `query_id` and `EXPLAIN actions = 1, compact = 1, pretty = 1, indexes = 1` — [diagnose slow queries](https://clickhouse.com/docs/guides/clickhouse/performance-and-monitoring/diagnose-slow-queries)
- Cost-weighted ranking (last9): `… GROUP BY normalized_query_hash ORDER BY avg_ms * runs DESC LIMIT 10`; failed queries: `SELECT type, exception, count() AS failures FROM system.query_log WHERE type IN ('ExceptionBeforeStart','ExceptionWhileProcessing') AND event_time > now() - INTERVAL 1 HOUR GROUP BY type, exception ORDER BY failures DESC LIMIT 10` — [last9](https://last9.io/blog/clickhouse-monitoring)
- Altinity "Handy queries for system.query_log": most resource-intensive by `normalized_query_hash` with `UserTime`, `DiskReadTime`, `NetworkReceiveTime` from ProfileEvents; A/B comparison of two `query_id`s on ProfileEvents (show diffs > 5 %); incomplete/slow queries (`countIf(type='QueryFinish')` vs starts, > 100 s); most-selected columns (`arrayJoin(columns)`), most-used functions (`used_functions`), WHERE-clause column usage, "worst offender" `DENSE_RANK()` over 33 dimensions — [Altinity query_log KB](https://kb.altinity.com/altinity-kb-useful-queries/query_log/); sibling pages "Compare query_log for 2 intervals", "Debug hanging thing", "Ingestion metrics from system.part_log", "Number of active parts in a partition", "Parts consistency", "Database Size - Table - Column size" — [Altinity useful queries index](https://kb.altinity.com/altinity-kb-useful-queries/)
- query_log columns: `type ∈ {QueryStart, QueryFinish, ExceptionBeforeStart, ExceptionWhileProcessing}`, `query_duration_ms`, `read_rows/bytes`, `written_rows/bytes`, `result_rows/bytes`, `memory_usage` (peak), `peak_threads_usage`, `normalized_query_hash`, `query_kind`, `databases/tables/columns`, `exception_code/exception/stack_trace`, `used_functions`, `query_cache_usage`, `user/initial_user/initial_query_id`, `client_name/http_user_agent/log_comment`, `ProfileEvents`, `Settings`; "local to each node … use clusterAllReplicas()"; `log_queries`, `flush_interval_milliseconds` — [query_log docs](https://clickhouse.com/docs/operations/system-tables/query_log)
- ClickHouse Cloud **Query Insights** (Monitoring → Query insights): stat boxes; three time-series "query volume, latency, and error rate broken down by query kind (select, insert, other)", latency chart p50/p90/p99; "Recent Queries" table "grouped by normalized query hash and user", filter/sort any field, column picker (tables, p90, p99…); per-query flyout with "Query Info" (aggregate frequency/perf) and "Query History" (individual runs, expandable "Settings and Profile Events"); reads `system.query_log` — [Query Insights docs](https://clickhouse.com/docs/cloud/get-started/query-insights). A third-party summary adds a "Slowest Queries" view sorted by P99 with "full query text, execution plan, resource usage breakdown, and call frequency" — [oneuptime](https://oneuptime.com/blog/post/2026-03-31-clickhouse-cloud-query-insights/view) (secondary source)
- duyet/clickhouse-monitoring (now "chmonitor"): pages Overview ("30+ charts"), Cluster Topology (nodes, shards, replicas, Keeper quorum), Cluster Insights ("findings, record-breaking queries, storage statistics"), Queries ("Running, slow, failed, and historical queries"), Data Explorer ("table size, parts, compression, TTLs"), Replication ("Merges, mutations, replication queue, Keeper"), AI Agent, read-only SQL Console with history and EXPLAIN; CLI `chm` with "live TUI and chm doctor"; MCP for Claude/Cursor; "No DDL auto-application; recommendations remain advisory only" — [chmonitor README](https://github.com/duyet/clickhouse-monitoring)
- Grafana ClickHouse datasource ships dashboards `cluster-analysis.json`, `data-analysis.json`, `query-analysis.json`, `system-dashboards.json` (+ OTel ones) — [grafana/clickhouse-datasource dashboards dir](https://github.com/grafana/clickhouse-datasource/tree/main/src/dashboards) (panel contents not fetched)
- Tabix: "query monitoring with process view and KILL QUERY support … realtime metrics view based on system.metrics and system.events", but no "node status, replication, or distributed queries"; DBeaver: generic JDBC client with query plans and schema compare, no monitoring — [ClickHouse third-party GUI list](https://clickhouse.com/docs/en/interfaces/third-party/gui) via search summary

### Inferences
- The tuple that every UI shows per pattern — runs, p50/p95 duration, max memory, read bytes, failure count, example text, users — is the table cobserve should draw; cobserve's unique addition is the Redash person resolution (`r_redash → j.petrova`) applied to history, which none of the surveyed tools have.

## Key question 4 — Node health signals that predict incidents, and recommended thresholds

### Takeaway
Two published threshold sets exist: ClickHouse's own (in metric descriptions and the Cloud dashboard guidance) and Altinity's operator alert rules. They agree on the leading indicators: parts per partition, delayed/rejected inserts, replication delay/readonly, Keeper session count, disk-full projection, uptime (restart), settings/version drift, detached parts, mutations backlog.

### Cited Findings
- Altinity operator alert thresholds (PromQL on `chi_clickhouse_*` = `system.metrics/events/asynchronous_metrics`): `Uptime > 1 < 180` warning (restart); `DistributedFilesToInsert > 50` high; `RejectedInserts` increase critical; `DelayedInserts` increase high; `MaxPartCountForPartition > 100` high; rows per INSERT ≤ 1000 warning ("use Buffer table or async_insert"); `LongestRunningQuery > 600` high; `QueryPreempted > 0` warning; `ReadonlyReplica > 0` high; `ReplicasMaxAbsoluteDelay > 300` high; connections `HTTP+TCP+MySQL > 100` warning; running queries > 80 warning; `ChangedSettingsHash` delta warning; `VersionInteger` delta warning; `ZooKeeperHardwareExceptions` increase critical; `ZooKeeperSession > 1` critical; `predict_linear(DiskFreeBytes[1d], 86400) < 0` high; `ReplicatedPartChecksFailed`, `ReplicatedPartFailedFetches`, `ReplicatedDataLoss` increase high; `SlowRead` increase high; mutations > 100 high; `DetachedParts > 0` high; Kafka pool exhausted / commit failures / consumer errors / rebalances high — [prometheus-alert-rules-clickhouse.yaml](https://raw.githubusercontent.com/Altinity/clickhouse-operator/master/deploy/prometheus/prometheus-alert-rules-clickhouse.yaml)
- Altinity monitoring KB severities: `DelayedInserts`/`RejectedInserts` critical; `DistributedFilesToInsert` "should not continuously increase" medium; `ReplicatedDataLoss` any increase high; detached parts present medium; `ReadonlyReplica` high; `SELECT value FROM system.metrics WHERE metric = 'Query'` against default max 100; "scraped metrics are not a complete history. Short-lived states between scrapes can be missed" → supplement with `query_log` — [Altinity monitoring KB](https://kb.altinity.com/altinity-kb-setup-and-maintenance/altinity-kb-monitoring/)
- ClickHouse's own level: `MaxPartCountForPartition` "larger than 300 indicates misconfiguration, overload, or massive data loading" — [asynchronous_metrics docs](https://clickhouse.com/docs/operations/system-tables/asynchronous_metrics); last9 restates it as alert ">300 for 15 min — ClickHouse's own warning level, well before delays start", plus `ReplicasMaxAbsoluteDelay > 300` for 10 min, `ReadonlyReplica > 0` for 5 min, failed > 1 % for 10 min — [last9](https://last9.io/blog/clickhouse-monitoring)
- Altinity "how much is too much": parts per table ~5,000 max; partitions system-wide "several dozen thousands"; inserts "dozen inserts per second maximum"; replicated tables "few hundreds is still acceptable" with real-time inserts in dozens; materialized views/projections per table "up to few"; disk per shard < 10 TB compressed — [Altinity KB how-much-is-too-much](https://kb.altinity.com/altinity-kb-schema-design/how-much-is-too-much/)
- Ingestion from `part_log` (Altinity): per `query_id` → `number_of_parts_per_insert`, `rows_per_insert`, `inserts_per_minute`; "Should not be more often than 1 new part per table per second (60 inserts per minute)"; per-minute query `SELECT toStartOfMinute(event_time) t, database, table, count() c, round(avg(rows)) FROM system.part_log WHERE event_date >= today() AND event_type = 'NewPart' GROUP BY database, table, t ORDER BY t` — [Altinity ingestion KB](https://kb.altinity.com/altinity-kb-useful-queries/ingestion-rate-part_log/)
- Memory ceiling: cobserve already uses `MemoryTracking` vs `max_server_memory_usage`; the `Memory (host)` dashboard adds `MergesMutationsMemoryTracking` and "ClickHouse vs Kernel Drift" (tracked vs RSS) as charts — [StorageSystemDashboards.cpp](https://raw.githubusercontent.com/ClickHouse/ClickHouse/master/src/Storages/System/StorageSystemDashboards.cpp)

### Inferences
- A single cheap "health row" per node that cobserve does not have yet: `SELECT (SELECT value FROM system.asynchronous_metrics WHERE metric='MaxPartCountForPartition'), (…'ReplicasMaxAbsoluteDelay'), (…'Uptime'), (SELECT value FROM system.metrics WHERE metric='ReadonlyReplica'), (…'DelayedInserts'), (…'ZooKeeperSession'), (SELECT min(free_space/total_space) FROM system.disks)` — seven numbers, each with a published threshold to colour by, each printable with its denominator (1000/3000 parts; 300 s; 1 session).
- Tracked-vs-RSS drift is a realistic Paysera signal: cobserve's "server · caches · merges" row is where it would land.

### Gaps
- Altinity's Grafana dashboard JSON (what panels, what thresholds) was not opened.
- No source gives a threshold for `BackgroundMergesAndMutationsPoolTask` other than "compare to pool size"; treat as ratio with denominator from `BackgroundMergesAndMutationsPoolSize`.

## Key question 5 — Query-level forensics for a running query (chdig's "query details" as the model)

### Takeaway
A read-only user on 24.10/24.11 can get everything chdig shows for one query except symbolised stack traces: live `ProfileEvents`/`Settings`/`peak_memory_usage` from `system.processes`, memory-over-time from `query_metric_log` (24.11+), the plan/pipeline/estimate from `EXPLAIN`, the server log lines from `text_log`, and after it finishes the processor profile and MV breakdown.

### Cited Findings
- `system.processes` exposes `ProfileEvents` (map), `Settings` (changed ones), `peak_memory_usage`, `total_rows_approx` (enables a progress %), `thread_ids`/`peak_threads_usage`, `normalized_query_hash`, `is_cancelled`, `is_all_data_sent`, client identity including `client_agent` ("AI coding agent detected (e.g., claude-code)") — [processes docs](https://clickhouse.com/docs/operations/system-tables/processes)
- chdig's per-query actions: Query details, Query profile events ("ProfileEvents listing with auto-refresh for running queries"), Query processors, Query views, Query metric log, Query threads, EXPLAIN SYNTAX/PLAN/PIPELINE/INDEXES, PIPELINE graph in browser, logs, copy, kill — [Actions.md](https://github.com/azat/chdig/blob/main/Documentation/Actions.md), [Queries.md](https://github.com/azat/chdig/blob/main/Documentation/Queries.md)
- `EXPLAIN PLAN indexes=1` shows "index types, conditions, and part/granule filtering"; `EXPLAIN ESTIMATE` returns `parts, rows, marks` per table; `EXPLAIN PIPELINE graph=1` emits DOT — [EXPLAIN docs](https://clickhouse.com/docs/sql-reference/statements/explain)
- `system.query_metric_log`: `SELECT event_time, memory_usage, peak_memory_usage FROM system.query_metric_log WHERE query_id = ? ORDER BY event_time` reveals growth pattern — [query_metric_log docs](https://clickhouse.com/docs/operations/system-tables/query_metric_log)
- `system.processors_profile_log` example: `ExpressionTransform` with ~1 s `elapsed_us` vs a source with equal `output_wait_elapsed_us` = downstream back-pressure — [processors_profile_log docs](https://clickhouse.com/docs/operations/system-tables/processors_profile_log)
- `system.stack_trace` requires `allow_introspection_functions = 1`, symbolised via `addressToSymbol`, `addressToLine`, `addressToLineWithInlines`, `demangle` with `arrayMap` — [stack_trace docs](https://clickhouse.com/docs/operations/system-tables/stack_trace)
- chdig's extra profiling needs server-side settings (`log_query_threads`, `trace_profile_events`, `opentelemetry_start_trace_probability`, `query_metric_log_interval`) — [FAQ.md](https://github.com/azat/chdig/blob/main/Documentation/FAQ.md)

### Inferences
- A "query drawer" for cobserve: header (user → person, Redash query id from `log_comment`/`http_user_agent`, elapsed, `read_rows/total_rows_approx` as a progress bar with denominator), a ProfileEvents delta column (per poll, like cobserve's CPU delta), a memory sparkline from `query_metric_log` (24.11) or cobserve's own poll history (24.10), and three on-demand tabs: EXPLAIN PLAN indexes=1, EXPLAIN ESTIMATE, text_log tail by `query_id`.
- Symbolised stack traces are out: `allow_introspection_functions` is a user-level setting that a `readonly=1` HTTP user cannot set, and the INTROSPECTION grant is unlikely on a monitoring user.

### Gaps
- Whether `log_processors_profiles`, `log_query_views` or `query_metric_log` are on by default for Redash's `r_redash` sessions is unknown; if not, those two tables will be empty for the queries that matter.

## Key question 6 — Redash: what admins monitor, which APIs expose it, any queue tools

### Takeaway
Redash exposes exactly three monitoring surfaces: `/status.json` (counts and Redis/Postgres sizes, `outdated_queries_count`), `/api/admin/queries/rq_status` (queues with started jobs and queued counts, workers with heartbeats and job counters) and `/api/admin/queries/outdated` (scheduled queries past due). "Overdue" is computed by `should_schedule_next()` with a `2**failures` minute back-off. No dedicated Redash queue monitor exists beyond generic RQ tools (rq-dashboard, rq-exporter).

### Cited Findings
- `/api/admin/queries/outdated` returns `{"queries": QuerySerializer(outdated_queries, with_stats=True, with_last_modified_by=False), "updated_at": manager_status["last_refresh_at"]}`; `/api/admin/queries/rq_status` returns `rq_status()`; both require super-admin login — [redash/handlers/admin.py](https://github.com/getredash/redash/blob/master/redash/handlers/admin.py)
- `rq_status()` = `{"queues": …, "workers": […]}`; each queue: `name`, `started` (list of jobs with `id, name, origin, enqueued_at, started_at, meta`), `queued` (count); each worker: `name, hostname, pid, queues, state, last_heartbeat, birth_date, current_job ("id (function_name)"), successful_jobs, failed_jobs, total_working_time`; helpers `get_redis_status()` (memory), `get_queues_status()`, `get_db_sizes()` — [redash/monitor.py](https://raw.githubusercontent.com/getredash/redash/master/redash/monitor.py)
- `/status.json` fields: `dashboards_count, queries_count, query_results_count, unused_query_results_count, redis_used_memory, redis_used_memory_human`, database sizes, manager `outdated_queries_count`, `last_refresh_at`; `outdated_queries_count` "encompasses queries that are IN PROGRESS, WAITING, or have errors preventing refresh"; maintainer: task lists "are not 100% reliable", use "the same API the UI uses" — [discuss.redash.io #683](https://discuss.redash.io/t/monitoring-the-status-of-tasks-using-a-http-request/683); the tasks page "isn't available through a documented API" — [discuss #10180](https://discuss.redash.io/t/getting-data-from-admin-queries-tasks-view/10180)
- Known failure modes: after a Redis flush `/api/admin/queries/outdated` crashes on empty `manager_status["last_refresh_at"]` — [discuss #10029](https://discuss.redash.io/t/getting-issues-in-function-outdated-queries-in-redash-redash-handlers-admin-py/10029); jobs "stuck in RQ status view … even though they aren't actually running in the database or occupying workers" — [discuss #11126](https://discuss.redash.io/t/queries-stuck-in-rq-status-view/11126); request for queue scheduling visibility — [discuss #8199](https://discuss.redash.io/t/redis-queue-scheduling-monitoring-visibility/8199)
- Overdue logic: `should_schedule_next(previous_iteration, now, interval, time, day_of_week, failures)` — `next = previous + interval` (or next `time`/`day_of_week`), then `if failures: next += timedelta(minutes=2**failures)`; `Query.schedule_failures` column; `retrieved_at` comes from Redis `scheduled_queries_executions` or `latest_query_data.retrieved_at`; "until" disables — [redash/models/__init__.py](https://raw.githubusercontent.com/getredash/redash/master/redash/models/__init__.py)
- Query serializer fields: `id, latest_query_data_id, name, description, query, query_hash, schedule, api_key, is_archived, is_draft, updated_at, created_at, data_source_id, options, version, tags, is_safe, user, last_modified_by`, with `with_stats=True`: `retrieved_at, runtime` — [redash/serializers/__init__.py](https://raw.githubusercontent.com/getredash/redash/master/redash/serializers/__init__.py)
- Architecture: "three worker services draining separate RQ queues for ad-hoc queries, scheduled refreshes, and maintenance tasks, with Redis serving as the job broker" — [railway redash template](https://railway.com/deploy/redash-analytics.md)
- Generic RQ tooling: `rq-exporter` (Prometheus; `rq_workers`, `rq_jobs` by queue/status, `rq_job_successful_total`, `rq_job_failed_total`, `rq_working_seconds_total`; port 9726) — [rq-exporter on PyPI](https://pypi.org/project/rq-exporter); RQ's own monitoring docs: `rq info` and rq-dashboard — [python-rq monitoring](https://python-rq.org/docs/monitoring/); worker-death signal: "a rising started-but-never-finished count indicates a worker-health problem" — [dev.to RQ monitoring](https://dev.to/piperadar/monitoring-python-rq-jobs-what-to-watch-and-how-to-get-alerted-3h07)

### Inferences
- cobserve already draws `rq_status` (view 2). What it does not draw and could, from the same two endpoints plus `/api/queries`: (a) **scheduled queries overdue** — list from `/api/admin/queries/outdated` with `schedule.interval`, `retrieved_at`, `schedule_failures` → "due 2 h ago, 3 failures, next retry in 8 min" (the `2**failures` back-off makes "silently stopped refreshing" dashboards explainable); (b) **worker health** — `last_heartbeat` age, `failed_jobs/successful_jobs`, `total_working_time`, `birth_date` (a worker that restarted); (c) **heaviest schedules** — `/api/queries` sorted by `runtime` × refresh frequency to name the dashboards that keep the queue warm; (d) **Redis memory** from `/status.json`.
- Redash's own "runtime" per query is the bridge to ClickHouse: `query_hash` + `runtime` vs `query_log.query_duration_ms` for the same `log_comment`/user shows whether the slowness is ClickHouse or the Redash worker.

### Gaps
- Whether `schedule_failures` is included in the serialized query payload was not confirmed (not in the field list the serializer page showed).
- No Redash-specific queue monitor was found beyond generic RQ tools; a search for one returned none.

## Key question 7 — Airflow TUI/CLI tools (2024–2026)

### Takeaway
The one serious Airflow terminal UI is **flowrs** (Rust, ratatui, REST API, multi-environment, trigger/clear/mark actions, inline logs). It is a management tool; nothing surveyed does what cobserve's view 5 does (a day timeline per DAG) — so cobserve's differentiation is already real, and flowrs' ideas worth copying are environment switching, task-instance history with retries, and inline logs.

### Cited Findings
- "Flowrs is a TUI application for Apache Airflow that allows you to monitor, inspect and trigger Airflow DAGs from the comforts of your terminal", built on ratatui; installs via Homebrew/uv/cargo; managed services: Conveyor, MWAA, Google Cloud Composer, Astronomer; self-hosted via `flowrs config add`; auth: HTTP Basic, bearer tokens (static or command-generated), session cookies; six themes; config `~/.config/flowrs/config.toml` — [flowrs README](https://github.com/jvanbuel/flowrs)
- Screens: DAG list "names, paused state, last run status, duration"; task-instance view "historical task instance status (success / failed / queued / running), retry counts, and execution time"; logs render in the terminal; actions: trigger (with config overrides), clear task instances, mark success/failed; arrow keys + Enter navigation; pick server at startup — [x-cmd flowrs page](https://x-cmd.com/install/flowrs/)
- "reads the same Airflow backend as the Web UI — live status shown in the Web UI is also shown in flowrs" — [search summary of flowrs sources](https://terminaltrove.com/flowrs/); Data Minded: "Flowrs is a Rust TUI for Apache Airflow that lets you manage all your environments from one terminal" — [dataminded](https://www.dataminded.com/resources/managing-airflow-at-scale-with-flowrs-a-rust-based-terminal-ui)

### Inferences
- flowrs' write actions (trigger/clear/mark) are the interesting half for engineers, and exactly the half cobserve excludes; cobserve could offer the read half flowrs has that view 5 lacks: retry counts per task instance, duration vs the DAG's historical median, and multi-environment (prod/stage) switching.
- Airflow 3's own `airflowctl` remote CLI exists as a scripting surface (from memory, not verified here — see Gaps).

### Gaps
- flowrs' supported Airflow versions (2.x vs 3.x REST API) and full keymap were not in any fetched page (README fetch returned only the install/auth sections).
- Airflow 3 `airflowctl` and Astronomer `astro` CLI capabilities were not researched within the call budget.

## Key question 8 — AI-assisted diagnosis in monitoring tools (2025–2026): what shape works

### Takeaway
The 2025–26 pattern across ClickHouse Cloud, chmonitor, Grafana and Datadog is the same: an agent that reads the same read-only data the UI shows, forms hypotheses, tests them against telemetry, and returns a structured report (findings, evidence, next steps) that the human can steer mid-run — never one that applies changes. cobserve already has the hardest part (Claude Code in-app, read-only SQL); what is missing is the *structured hand-off*: pre-filled context and a report shape.

### Cited Findings
- ClickHouse Cloud Assistant: "lets you use natural language to analyze data in a ClickHouse Cloud service"; two modes — Agent mode ("Multi-step reasoning over schema and metadata", shows "expandable intermediate thinking or planning steps") and Docs AI ("Q&A grounded in official ClickHouse documentation"); context = "Active tabs and saved queries, Database schemas, Dashboards and metadata"; org-level enablement and a consent dialog — [Ask AI docs](https://clickhouse.com/docs/products/cloud/features/ai-ml/ask-ai); search summary claims it "now handles about 70% of internal analytics use cases" (secondary, from the same page's search snippet)
- chmonitor: "AI advisor: projections, skip indexes, PREWHERE, MVs"; "Built-in AI agent + MCP for Claude / Cursor"; "No DDL auto-application; recommendations remain advisory only" — [chmonitor README](https://github.com/duyet/clickhouse-monitoring)
- Grafana Assistant Investigations (GA 2026-07-29): "point it at an alert or incident, exploring metrics, logs, traces, and profiles, building hypotheses, and producing a structured report with findings, supporting evidence, and recommended next steps"; starts manually or "automatically through alert enrichment … or via IRM webhooks"; "by the time you open it, the work is already in progress"; users "follow the investigation in real-time and provide hints or corrections"; reachable from UI, Slack, MCP server, or terminal via `gcx` — [Grafana what's new](https://grafana.com/whats-new/2026-07-29-assistant-investigations-is-now-generally-available-in-grafana-cloud/); case study: root cause "in eight minutes, 20 minutes before the on-call team" — [Grafana blog](https://grafana.com/blog/a-tale-of-two-incident-responses-how-our-ai-assist-helped-us-find-the-cause-3-5x-faster/)
- Datadog Bits AI SRE: "forming hypotheses, testing them using live telemetry data, and following promising evidence to a root cause"; newer version "recursively generates deeper root cause hypotheses until it exhausts the search space", "audit-ready root cause analyses in minutes" — [Datadog building Bits AI SRE](https://www.datadoghq.com/blog/building-bits-ai-sre.md), [helpnetsecurity 2025-12-03](https://www.helpnetsecurity.com/2025/12/03/datadog-bits-ai-sre-agent/)
- ClickHouse now records `client_agent` ("AI coding agent detected (e.g., claude-code)") in `system.processes` — [processes docs](https://clickhouse.com/docs/operations/system-tables/processes)

### Inferences
- The shape that fits cobserve: a one-key "investigate this" on any red row (node, query, DAG, queue) that opens a Claude session pre-seeded with the row's numbers, the §5 formulas they came from, and a fixed read-only toolset (the same SQL the views run), and that writes back a short structured note (hypothesis → evidence → next step) into the tape. That is Grafana's "already in progress when you open it" without any write path.
- Because `client_agent` is now recorded, cobserve's own Claude sessions will be visible in `system.processes`; the UI should label those rows so an investigation does not chase itself.
- Advisory-only is the industry norm (chmonitor says so explicitly), which matches the read-only rule.

### Gaps
- Whether the ClickHouse Cloud assistant can read `system.query_log` for performance diagnosis is not stated in its docs (the page only covers data analysis and docs Q&A).
- ClickHouse's official MCP server (believed to default to read-only) was not verified in this session.

## Appendix — cost rules of thumb gathered across sources (for the implementation)
- `*_log` tables are per node, rotate (`merge('system','^query_log')`), and must be bounded by `event_date`/`event_time`; Cloud/docs recommend `clusterAllReplicas()` which needs remote grants — cobserve's per-node HTTP fan-out avoids that ([query_log docs](https://clickhouse.com/docs/operations/system-tables/query_log), [diagnose guide](https://clickhouse.com/docs/guides/clickhouse/performance-and-monitoring/diagnose-slow-queries)).
- `system.metric_log` and `asynchronous_metric_log` are "safe to truncate or drop" and may not exist if disabled; `error_log` 24.8+; `query_metric_log` 24.11 (verify); `metric_log` schema differs across 24.x/25.x but alias columns keep `ProfileEvent_*`/`CurrentMetric_*` SQL valid ([metric_log docs](https://clickhouse.com/docs/operations/system-tables/metric_log)).
- `system.zookeeper` refuses queries without `path`; `system.stack_trace` is expensive and needs introspection grants; `system.backups` forgets on restart; `system.errors` counts can rise on successful queries ([zookeeper](https://clickhouse.com/docs/operations/system-tables/zookeeper), [stack_trace](https://clickhouse.com/docs/operations/system-tables/stack_trace), [backups](https://clickhouse.com/docs/operations/system-tables/backups), [errors](https://clickhouse.com/docs/operations/system-tables/errors)).
- Redash admin endpoints need a super-admin API key and are "not 100% reliable" for task lists; cobserve's local rig only has an admin key read from the local DB (CLAUDE.md) ([admin.py](https://github.com/getredash/redash/blob/master/redash/handlers/admin.py), [discuss #683](https://discuss.redash.io/t/monitoring-the-status-of-tasks-using-a-http-request/683)).
